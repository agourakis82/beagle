# Program Lineage

## Purpose

This document explains how the current Beagle identity emerged, so the project
does not confuse:

1. incubation lineage
2. operational proof lineage
3. constitutional lineage

## Lineage summary

### Incubation lineage

`darwin-v2` was the incubation and proving tree for the Darwin HPC stack.

That tree proved early boundaries, contracts and operational shape before the
canonical integration target became the Beagle repository.

### Repo-native import lineage

The first Beagle-native lineage step was documentary and contractual:

1. `B9` imported stable Darwin HPC docs, contracts and templates
2. `B10` anchored object-backed publication and lifecycle semantics
3. `B11` anchored object-backed retrieval and result catalog/query semantics

This gave Beagle a repo-native Darwin/HPC documentation and contract base
without pretending the runtime was already fully materialized.

### Operational kernel lineage

The next lineage step built the operational kernel inside Beagle:

1. `B12.3` established the internal control surface line
2. `B12.4` attached the workspace plane
3. `B12.5`, `B12.6`, `B12.7`, `B12.8` proved repo-aware, operator and GPU
   workflow loops
4. `B12.2b` and `B12.2c.*` closed the bounded cheap provider lane

This shifted Beagle from a documentation target to an operating runtime path.

### Dev-plane lineage

The `B13.*` sequence moved from viability to disciplined default operation:

1. `B13.1` cut over the canonical dev plane
2. `B13.2` proved the repo-native dev loop
3. `B13.3` promoted the scoped default dev plane
4. `B13.4` proved fallback discipline
5. `B13.5` expanded the promoted dev-plane scope
6. `B13.6` proved sustained repeated use under real loops

This is the point where `beagle-cluster` stopped being a pilot convenience and
became the canonical default development plane.

### Workstream OS lineage

The `B14.*` sequence turned a proven runtime path into a governed workstream
system:

1. `B14.1` cut over the first real workstream
2. `B14.2` created the repo-native workstream registry/spec layer
3. `B14.3` created explicit recipes and execution graphs
4. `B14.4` formalized promotion / hold / rollback / recovery governance

This is the point where Beagle stopped being just a place to run workflows and
started becoming a workstream operating system.

### Internal operating surface lineage

`B15.1` created the first internal control room:

1. one internal operator surface
2. one canonical workstream visible there
3. repo-native contract, recipes, governance, handoff and last-result state
   consolidated there

That established the first operator-facing internal mission surface without
widening into public UI or reopening lower layers.

### Constitutional lineage

`B15.2` is the constitutional bridge:

1. it does not add a new subsystem
2. it does not widen the runtime
3. it states what Beagle already is operationally
4. it states what Beagle is meant to become aspirationally
5. it freezes the planes, lanes, workstream model and non-negotiables that now
   define project identity

## Current interpretation

The current lineage means:

1. operational Beagle is already real
2. aspirational Beagle is now named and bounded
3. future growth should extend the workstream operating model, not restart the
   platform from scratch

## Lineage guardrail

The program must not regress into:

1. parallel canonical servers
2. VM-first operation by inertia
3. implicit workstreams without repo-native contract
4. ad hoc provider sprawl as roadmap center
5. public-surface widening before the internal operating model asks for it
